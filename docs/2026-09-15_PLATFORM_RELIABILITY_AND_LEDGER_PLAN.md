## 1. 范围与原则

首批处理 SSH 重连、单机时区、交接台账、手动提交耗时、完成文案和 QC 展示。各项独立小提交，按依赖逐项验收，不合并成一次大重构。

- 云端 Airflow 准备/启动使用 200；单机使用用户指定的 96/97；18 仅作为跳板，qsub 例外。
- 严禁改动 `prepare_wgs_batch.py` 的接口和业务逻辑，不改变 local、SGE、pending 的业务规则。
- 复用 Registry、Adapter、OBS lease、现有投影、状态徽标和刷新 Hook。不把 WGS/GATK 合成充满条件分支的大 DAG。
- 本计划不授权新分析、重启失败批次、清理生产数据、修改 pending 文件或删除历史 Kubernetes Jobs/ConfigMaps。
- 本计划最初只维护文档，现已获用户继续源码开发授权；测试在 BS10610，生产发布仍须按[环境边界](34_TEST_PRODUCTION_RELEASE_BOUNDARY.md)获得当次授权并核验实际挂载。

## 3. 首批任务卡

### REL-01：SSH 有界重连与身份复用

责任领域：Airflow/runtime。先做，作为提交稳定性的基础。

- 仅对明确尚未执行远端命令的临时连接故障重试，例如连接超时、拒绝连接、banner 握手失败。最多三次连接，间隔 5 秒、10 秒，保留单次连接超时。
- 认证、host key、Python/业务异常和目录冲突不重试；不能把所有 exit 255 都当网络重试。
- 已发出命令后断线属于执行结果不确定：先按原身份查状态/receipt，禁止盲目重复准备。
- 复用 analysis_id、attempt、execution_id、generation 和请求，不重新登记、不重复消费 pending。与请求可见性重试分开，避免 Airflow 整阶段和 SSH 双层重复执行。
- 日志给出安全的尝试次数与故障类型，不输出凭据。不改变 GATK 已有重试语义。

验收：少量连接故障、认证失败、执行后断线用例证明分类正确且没有重复副作用。回滚：恢复 runner/DAG 对应版本，不回滚业务数据。

### REL-02：96/97 单机运行时区约束

责任领域：runtime；与 REL-01 相邻实施但独立提交。

- 在选定 96/97 的实际执行入口显式注入进程环境 `TZ=Asia/Shanghai`，在 Python 启动前生效，并由 prepare 和子进程继承。
- 平台调用与文档中的手动单机调用采用同一约束；不得依赖登录 shell 或宿主机默认时区。已有平台 wrapper/gate 承担环境设置，不改原 WGS 脚本。
- 不修改服务器系统时区。API/数据库/receipt 继续保存带时区的 UTC 时间，UI 明确显示时区；运行所需本地时间与状态存储时间是两个层次。
- 计时采用单机单调时钟或已同步的已有计时字段，不直接相减不同主机的无时区时间。

验收：最小环境探针证明入口和子进程均得到 Asia/Shanghai，96/97 目标选择不被改写，UTC 状态时间格式不变；不为验证而执行完整分析或修改 pending。

### LEDGER-01：交接台账语义与 Sample UI 对齐

责任领域：backend 投影/API 与 frontend，各自小提交，接口文档同步。

- 复用 Sample 表格、字体、间距、筛选和 StatusBadge，不再追加独立 CSS overlay。
- 主表只显示当前 pending，服务器过滤与分页总数一致；捞回后退出主表，不删除数据库样本或历史。
- 主列为样本/家系、来源分析批次、Status、详情；中文原因跟随状态。删除 `Origin → target`、`Last good / sync` 主列，同步诊断放详情，仍保留明确的同步异常提示。
- 来源用有凭据的来源分析批次，必要时取记录的分析批次；禁止用上机批次或猜测目录名。修正现有 origin 投影，保持字段/筛选兼容并更新 API 契约，不重写历史 receipt 身份或 HMAC。
- 原因采用有限、安全的映射；未识别原因显示“待核对原因”，不展示内部代码或未经筛选的临床自由文本。
- 历史有 consumed 凭据才显示“已交接至某批次”；只有 selected 凭据显示“已纳入某批次”；仅从 pending 消失则显示“已移出待交接，接收批次未确认”。不显示 `- → -`，不把交接完成当分析/QC 完成。
- “0910A、0911B 各三条”是回滚后的历史核对基线；如果后续已合法消费，以最新证据为准，不能为迎合旧截图强行改状态。
- 通过正常 worker 投影刷新，不更改原 WGS 脚本和 pending 文件。

验收：少量合成记录覆盖当前 pending、已消费、只有 selected、无接收凭据、缺原因和同步失败；核对分页、来源和 Sample 样式。回滚代码，不删除历史或恢复旧 pending。

### SUBMIT-01：三阶段系统等待累计不超过一分钟

责任领域：backend/Airflow/frontend，先定位再最小修复。

用户确认的口径：健康网络、无资源排队时，三阶段累计系统等待目标 ≤60 秒，不包含人工复核时间和正式分析耗时。排队和异常重试须单独显示，不能暗中从耗时中隐藏。

三个计时段：

1. 提交至样本预览可用。
2. 确认配置至执行预览可用。
3. 最终启动至后台受理、前端展示已提交/排队。

先复用 Airflow 时间、runtime 状态和 receipt `timings_ms`，仅补齐 API 登记、调度排队、SSH/进程启动、原脚本、receipt/DB 发布和 UI 可见的缺失边界。可按需在 RunDetail 增加可选 `submission_timing`，缺值为未知而不是零；复用已有存储，不建遥测系统或新计时表。

- 针对观测到的重复查询、启动开销、固定等待优化；不预设 83 秒全部是网络或 Python 启动。
- 提交页使用单飞、响应完成后安排下一轮刷新；确认后立即刷新，活跃准备建议两秒轮询，后台降频。避免每轮获取无关完整详情/历史。
- 按 attempt/generation 防止旧响应覆盖新状态；服务端状态为准，不假完成、不取消三阶段确认。
- 不以新常驻服务、长期临床数据缓存、跳过校验或修改原脚本换取一分钟。
- 若原脚本或上游本身超过预算，明确记录未达标及瓶颈，另行确认必要变更，不能宣称已修复。

验收：最小轮询/旧响应测试，加一次受控准备的完整分段计时；故障重连单独验收。生产实际耗时在下一次获授权提交时核对，不自动重跑 0911A。

### TRACKER-01：完成文案统一

责任领域：API 展示契约/frontend。

- WGS、WES/GATK 在 Run Tracker 的整体成功终态统一展示 `Completed`，沿用同一成功徽标和样式；流程名称由 Pipeline 列表达。
- 使用公共终态展示映射，保持底层 pipeline ID、状态码、stage code 和 attempt 不变。阶段仍在运行或后续收集/传输未完成时，不因某个 workflow 已结束就提前显示整体完成。
- Run detail 的总体状态与 Tracker 保持一致；QC 通过/失败与运行完成仍独立，不把 Completed 当作 QC PASS。

验收：同一组成功、失败、运行中及“workflow 已结束但后续未完成”合成状态，核对两个页面；不全局盲目替换日志或阶段名称。

### QC-01：Run detail QC 判定与样式修复

责任领域：frontend，必要时由 backend 修正缺失的投影契约。

- 复用现有 `RunQcTab`、`QcMetric`、StatusBadge 和 Sample/Run detail 的表格规范。去掉“Metric judgments 内再逐列折叠”的堆叠呈现，不新建独立风格。
- 主表按现有 adapter/QC 定义展示关键指标、友好名称、值、单位和判定；单个样本详情集中展示适用阈值、中文原因及来源。原始字段/JSON 只作为可选诊断详情，不作为主界面列名。
- 逐项区分值缺失、策略缺失、不适用、尚未投影和真正无法判定；使用已有契约，确需新增原因时同步 API 文档。没有依据时明确“待判定/缺少判定依据”，绝不直接转 PASS 或用隐藏 unknown 掩盖问题。
- 信息型指标不参与整体失败/unknown 聚合；真正必需指标的缺失不能被排除。沿用现有 policy 的 required/适用性规则，不新设生信阈值或改变 QC 业务判定。
- 未知数值保留，原始 PASS 字符串不替代缺失策略；失败指标保持醒目。运行成功、来源 QC 状态和平台 QC 判定分开。

验收：复用少量已有 fixture 覆盖 pass/fail、信息型 unknown、缺值、缺策略、不适用、单位和字段名称；核对 WGS 与 WES/GATK 的实际展示路径，避免只修公共组件却遗漏 WGS 专用页。不跑完整生信分析。
