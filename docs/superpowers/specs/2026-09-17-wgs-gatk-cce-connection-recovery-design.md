## 1. 目标与边界

连接中断不等于分析失败；恢复连接不等于重新执行。

一次覆盖 WGS/GATK CCE 的上传、Master 创建、分析监控、发布、下载、
整理交付六个 runtime 步骤，以及 Airflow/后端对这些步骤的状态传递。
Step1–6 是 runtime 语义，不要求修改页面或 DAG 现有编号、名称、步骤顺序。

保留 analysis_id、业务 attempt、冻结版本/配置/目录及成功产物。
复用现有 Registry/adapter、操作认证、执行记录、generation、checkpoint、
发布记录、交付记录及 lease，不新增服务、锁体系、数据库表或业务状态枚举。

2026-09-22 新增：对第 3.1 节两类已确认的临时基础设施故障，允许设计
有界自动断点续跑，必要时由既有受控 Resume 原语替换已失败的 Master。
这是对原版“排除自动 Master 替换”的唯一范围扩展，不是通用失败重跑。

不包含 prepare、pending、生信参数、Local/SGE、Step7 清理、任意失败的自动
业务重跑、失败后自动日志打包、日志下载功能推广、镜像升级。
0919C 类配置样本数与 FASTQ 清单不一致、缺文件、自动查找/补传输入、改写
上传完成凭据均暂不纳入；保留现有人工纠正后续跑能力，不在本任务扩展它。
不合并测试分支的其他未发布功能；不修改冻结项目脚本以临时兼容。
生产 CLI/wheel 更新如确有需要，须随源代码修复单独列出发布对象并确认，
不能以本方案批准代替生产升级授权。

## 2. 依据与方案选择

前次只读诊断：测试任务的 Step3 因 `kubectl query failed` 退出，但查询到的
原 Master Job UID 与冻结 handoff 一致，仍为 active。该异常丢失底层 stderr，
不能事后断言一定是网络故障，也不能用错误摘要里的 current rule 推断 rule 失败。

基线源码存在以下差异：

- 两套 DAG 的只读 stage sensor 已有有限网络重试。
- GATK gate 的 Step3 子进程非零退出会直接落成 failed，先于 sensor 容错。
- WGS Step3 对 `kubectl query failed` 有按文本等待的兼容，但不足以区分
  认证/身份问题与连接故障，也不等于全链路恢复已实现。
- WGS 已有 resume_stage；后端当前明确限制 WGS CCE，GATK 不能直接调用。
- GATK SSH 派发失败、DagRun 失败投影也须与 runtime 的错误语义对齐。

选用“共用错误规则 + adapter 按原执行记录恢复”。只增加 Airflow 重试次数
不能修复底层已写入的错误终态；整步自动重跑则会重复创建/发布。
不合并两套 DAG，不建立新的连接恢复守护服务。

本轮比较的三种做法：仅加强查询重连无法恢复已退出的 Master；整个 DAG
自动重试可能重复 prepare/上传/发布；采用“查询重连 + 两类故障白名单 +
既有阶段 Resume”可复用身份与产物，因此选择第三种。失败批次号仅是需求
来源，不能作为代码判断条件；不通过本设计直接恢复任何历史真实批次。

## 3. 错误分类与重试责任

| 类别 | 决策 |
| --- | --- |
| 明确连接超时、重置、临时不可达，HTTP 408/429/5xx | 对只读查询有限重试 |
| 认证、权限、参数错误 | 不自动重试；记录控制/监控错误，不据此判定远端分析失败 |
| 身份、request hash、generation、Master UID 不匹配 | 阻止恢复；不切换对象 |
| 创建 Worker 时连接中断或 Gatekeeper 超时，导致 Master 退出 | 仅满足第 3.1–3.3 节全部条件才自动断点续跑 |
| 其他权威执行失败、业务失败或执行进程异常退出 | 真实步骤失败；不自动重跑、不降级成成功 |
| 查询失败、对象消失但无可靠终态、模糊的通用报错 | 执行状态待确认；禁止推断成功/失败或重发有副作用的操作 |

只读查询规则：首次查询后最多重试六次，30 秒起指数退避，单次等待上限300秒。
每次请求须有明确超时；同时受原步骤总超时约束，不无限延长执行期限。
一次成功的权威查询结束本轮连接故障，后续正常轮询不消耗该轮重试预算。

职责边界：

- Airflow 到后端：复用已有 sensor 重试。
- runtime 到 Kubernetes/远端服务：由只读查询的直接调用层负责。
- 传输工具：保留原有内部重试，不套整步重跑。
- 证据桥只采集日志/事件；其异常不覆盖权威分析状态。

同一故障不能逐层获得新预算。runtime 报告重试耗尽后，sensor 不把它重新
当作一次尚未处理的临时 HTTP 错误。重连次数、首次错误时间、耗尽原因及
最后确认时间沿用已有步骤/操作 JSON 记录保存；进程重启或重复点击不能
静默重置同一恢复操作的预算。新的人工作业恢复操作可获得一轮新预算。
该“新预算”仅指查询预算，不重置第 3.2 节的 attempt 级自动续跑次数。

错误需包含脱敏类别、退出码/HTTP 状态及简短原因，不公开 token、配置正文、
带凭据 URL 或原始完整 stderr。如果 CCE runtime 已吞掉原因，应在其正式
源代码修复，再按原发布流程交付；不能靠上层字符串猜测，也不能改写已冻结
bundle。旧通用错误归为“未分类、待确认”，不无条件自动重试。

### 3.1 本轮新增的两类自动续跑候选

| 类别（拟定内部代码） | 必须同时具备的源头证据 | 不足以触发的证据 |
| --- | --- | --- |
| `worker_create_transport_interrupted`（0918A 类） | 精确属于当前 Master 的 Worker Job 创建调用；RemoteDisconnected/Connection reset/ProtocolError 中明确的传输中断；该异常是导致本次 Master 退出的原因 | 任意日志含 timeout/ProtocolError、只读查询失败、只有 BackoffLimitExceeded |
| `worker_create_admission_timeout`（0919B 类） | 同一创建调用收到 HTTP500，结构化原因指向 `mutation.gatekeeper.sh` 的 `context deadline exceeded`，并导致当前 Master 退出 | 任意 HTTP500、Gatekeeper 策略拒绝、403、配额/参数/权限错误 |

两类均须有权威 Master 失败/退出证据，且没有冲突的生信 rule 失败证据。
Master 仍活跃则只接回监控；不能因为读到一条创建错误而替换正在运行的 Master。
未分类、退出原因缺失、多重根因、源头错误已被吞掉均转人工，不猜测。
OOM、磁盘不足、缺 FASTQ、校验失败、镜像拉取失败和真实 rule 非零退出
不因同时出现网络错误而获准自动恢复。现有插件内部重试次数不能凭假设填写，
开发时核对冻结版本，只在其最终失败后作一次候选判定，不叠加 Job POST 重试。

错误证据通过现有受信 runtime/事件采集入口绑定 pipeline、analysis_id、
attempt、execution_id、generation、request hash、Master UID、调用类型及
根因类别；保存脱敏摘要和受控证据引用。新增字段为拟定合同，不代表现有实现。
浏览器文案、未经绑定的日志文本或前端请求不能提供自动恢复授权。

### 3.2 两种独立且持久的预算

以下为本轮建议的默认值，待文档审阅后在开发合同固定，不是当前线上设置：

- 查询重连仍按原规则：额外 6 次，30 秒起指数退避、单次上限 300 秒。
- 自动计算恢复：同一 `pipeline + analysis_id + attempt` 最多 **2 次**，
  第一/第二次分别等待 **60 秒 / 180 秒**；两种根因共享该上限，不按新 UID、
  generation、DagRun、错误文本或服务重启重新计数。
- 第一次原始执行不计入这 2 次；续跑完成一部分 rule 后再次出现白名单故障，
  仍消耗同一 attempt 的剩余额度，不因出现新进度清零。
- 并发请求在既有事务/运行锁内预留同一恢复动作及序号；在有副作用的派发前
  持久记录。重复回调、超时重试、相同动作重放只接回该动作，不再扣次或提交。
- 原步骤总截止时间在首次执行时固定；替换 Master/换 DagRun 不重置期限。
  新执行只获得剩余时长；预算或期限耗尽后停止自动动作并明确转人工。
- 用户手动 Resume 不隐式重置自动额度；新增额度不属于本设计。手动操作仍可
  使用现有权限与断点流程，但必须与自动动作互斥，保留原恢复历史。

复用当前阶段/恢复操作 JSON 和 generation 历史保存 policy_version、
auto_recovery_count、next_retry_at、original_deadline、action_id、来源执行、
根因证据引用和结果。字段按接口开发任务落实，无新增数据库表/锁服务。
保存或读取预算失败时停止自动派发；不能把缺失字段解释为历史次数为零。
不为这项设计追溯启用已在运行/已失败的历史 attempt；启用时只对显式冻结了
该策略的新 attempt 生效，历史任务继续人工 Resume。

### 3.3 安全检查、派发与副作用边界

1. 由现有 WGS/GATK 阶段监控链在读取绑定的终态后提交恢复候选，后端既有
   recovery/action 层是唯一审批与预算所有者。observer 只提供证据，不能另开
   一套恢复循环；同一候选通过原失败执行身份及 Master UID 去重。
2. 核对启用策略、允许的根因、当前 attempt/config/release/workdir、剩余
   预算及总截止时间；暂停、取消、删除、Step7 或其他恢复动作存在时禁止派发。
   与 RUN-CONTROL 共用同一动作互斥/取消栅栏，用户停止操作优先于未派发恢复。
3. 确认旧 Master 终态、其 Pod 已退出，并完整查询本运行的 Worker Job/Pod。
   0918A 的创建响应丢失可能实际创建了 Worker，必须按原归属清单核对它。
   一次空列表不是不存在的充分证据；所有权不明、列表截断/不可读均阻止替换。
4. 同归属 Worker 仍活跃时先有限等待其自然结束，建议上限 10 分钟且受原步骤
   剩余期限约束；超限转人工。本功能不自动 kill Worker，不扩展批量清理。
   确认没有活动执行后，在派发临界点重新检查动作栅栏和身份。
5. 复用既有受限 Resume 原语，归档失败证据、记录前后 Master UID lineage，
   创建恢复 generation。只有确切拥有且已终止的旧 Master 对象可按原语替换；
   无法原子核对 UID/所有权的历史 bundle 禁用自动能力，不以同名对象代替。
6. 保留 analysis_id、attempt、冻结配置/版本/目录及成功输出，不执行 prepare、
   不消费 pending、不重新上传、不使用 forceall。Snakemake 按依赖与 incomplete
   标记执行未完成工作；某个未完成 rule 可从头重做，不承诺进程内存级续跑。
7. 创建响应再次丢失时按动作 journal、确定性对象身份、UID/handoff 查询接回，
   不立即提交第二份 Master。恢复序号只预留一次，查询失败不获得新恢复额度。
8. 旧失败 DagRun 的失败回调/lease 收尾受恢复动作栅栏限制；恢复沿用现有
   stage-resume DAG 路径，只进入当前阶段和必要下游。原阶段取得权威成功后
   才自动继续 Step4–6，不要求操作员逐阶段改状态。

延时/等待由现有 Airflow 编排调度持久动作实现，不新增定时守护服务；不能
把有副作用的 task 整体设为 retries=2。轮询耗尽、进程重启和回调丢失后，
现有编排读取持久动作接回；无法核实派发结果则转待确认，不能重建随机动作。

## 4. 各步骤恢复规则

| runtime 步骤 | 接回及续跑行为 |
| --- | --- |
| Step1 上传 | 原执行活跃则接回监控；确认进程退出后，用户续跑才复用 checkpoint 和成功对象补传 |
| Step2 创建 Master | 丢失响应先按原请求查询；已有 Master 则接回。只有明确原提交未发生且不存在在途创建，才允许同一请求重发 |
| Step3 分析监控 | 活跃 Master 仅重连；真实失败保留历史，两类白名单且全部门禁通过才按第 3.3 节自动断点续跑；其他失败转人工 |
| Step4 发布 | SSH 超时/响应丢失先查询原执行及发布记录；仍进行则接回、完成则确认成功；仅证明未启动且无在途派发时按同一动作安全再派发，否则待确认 |
| Step5 下载 | 原下载仍活跃则接回；确认退出后，用户续跑复用 checkpoint 和已验证文件 |
| Step6 整理交付 | 接回原进程，或依据已有 journal/交付记录续做未完成部分；不重新下载，不覆盖已交付结果 |

Step2 的一次空查询不充分证明创建请求未到达；必须与已有派发/执行记录
一起确认，依靠原任务确定性身份与服务端防重复创建能力，不新增随机 Master。
Step4 同样不能将“未拿到响应”等价为“发布未发生”。
0918A 的 Step4 120 秒 SSH 调用超时属于此处“结果不确定”，不是握手失败。
将其纳入原操作核对，不额外创建新的发布身份，也不重复已成功的 Step3。
同一 Step4 动作证明未发出后的重派发最多 2 次，复用持久序号、60/180 秒
等待与原截止时间；这是派发恢复预算，不消耗也不重置 Master 计算恢复预算。

只做必要身份、活跃执行和恢复记录检查；不全量扫描输出、计算历史文件哈希
或重新验证整个 release。现有结果允许存在。同任务旧锁按现有归属和活跃性
处理；其他任务持锁或无法确认活跃性则停止，不强行解锁。

传输 lease 不因查询失败、Airflow task 失败或超时直接释放。只有现有权威
终态/归属条件满足才能释放，避免原上传/下载仍运行时引入第二份执行。
本方案不改变 lease 数量、池配置或并发限额。

## 5. Airflow、后端和页面状态契约

区分执行结果与监控健康度，复用 `monitoring_health`、`message` 和原步骤
JSON/执行记录，不新增整套业务状态。通用失败不能直接冒充执行终态 receipt。

| 场景 | 调度与展示 |
| --- | --- |
| 有限重连中 | 保留最后确认的执行状态/进度；显示“连接中断，正在重连”及最后确认时间 |
| 重试耗尽或控制错误 | 停止自动查询；显示“监控中断，执行状态待确认”和原因，提供人工恢复入口 |
| 重连查到原执行仍活跃 | 接回正常监控，不重新派发，不增加业务 attempt |
| 重连取得权威成功 | 同步原步骤成功，放行必要下游 |
| 白名单失败，已受理自动恢复 | 保留失败执行历史，显示“自动续跑等待中（1/2）”及原因/下次时间；未启动前不声称分析运行 |
| 替换 Master 已确认开始 | 显示“自动续跑中（1/2）”；绑定新 generation，保留原 attempt 和断点 |
| 自动恢复耗尽/安全检查未通过 | 显示“自动续跑停止，需人工处理”；真实失败与执行状态待确认分别展示，不统一伪装为 running |
| 取得其他权威失败 | 明确步骤失败，保留原失败原因与断点 |
| 权威分析成功但日志采集异常 | 分析成功，监控 degraded，提示“分析完成，日志采集异常” |

Airflow task/DagRun 可因监控耗尽或控制错误结束为 failed，但后端不得仅据此
将远端分析投影为失败。失败回调、周期状态同步、runtime receipt 导入必须
遵守同一规则；不能只改页面文案而保留后端错误终态。

耗尽后的最后 running 是“最后确认状态”，不能继续对外宣称实时正常运行。
Tracker 和详情使用同一监控健康度/时间字段，进度冻结并明确过期，不继续
凭时间推进预估进度。无权威成功不启动下游；不能将监控 task 标成 success
来绕过依赖。身份校验失败也不能伪装成成功。
恢复动作状态使用现有操作字段和展示文案，不新增业务状态枚举。Tracker/详情
读取同一最新动作及当前 generation；旧 Master failed 仍作为历史保存，不能
覆盖新执行，也不能被改写为 success。剩余 rule 统计必须说明续跑分母口径，
等待时不增长百分比。恢复后仍由正常阶段回执推进，不增加手工改库步骤。

## 6. 恢复入口与幂等

复用运行操作面板和认证，通过 adapter 补齐 GATK 的阶段恢复能力。共用动作
语义和操作记录，不将 WGS 的所有运行时逻辑直接套到 GATK，也不走会增加
业务 attempt 并重新 prepare 的旧 resume 路径。

人工点击后的先后顺序：

1. 验证当前任务/attempt/冻结目录与配置身份。
2. 查询原执行及已有恢复操作；重复点击返回同一操作。
3. 原执行活跃：仅恢复监控；原步骤成功：同步状态并继续必要下游。
4. 进程确认退出：当前人工操作授权在该步骤原有断点能力内续跑。
5. 无法确认活跃性：保持待确认，不启动第二份。

只读查询本身不增加 generation；确需新监控进程或步骤执行时，用现有
generation/retry 记录留痕，明确绑定原远端执行。原执行的可信终态只能经
当前恢复操作验证后归入当前状态，旧失败事件不能直接覆盖新执行。
清除的是新执行的旧终止时间，历史记录不删除。

重开范围限当前步骤/监控和必要下游，已成功前置步骤不变。保留原生信
Master 失败后的人工续跑机制；新增自动入口仅适用第 3.1 节两类根因，且与
人工入口共享预算记录、身份校验及动作互斥，不提供无条件的自动 Master 替换。
界面复用现有控件，按情况显示“恢复监控”或“续跑”，不新增独立恢复页面。
