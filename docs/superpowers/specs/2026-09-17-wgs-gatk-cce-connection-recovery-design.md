不包含 prepare、pending、生信参数、Local/SGE、Step7 清理、自动 Master
替换、自动业务重跑、失败后自动日志打包、日志下载功能推广、镜像升级。

## 2. 依据与方案选择

前次只读诊断：测试任务的 Step3 因 `kubectl query failed` 退出，但查询到的
原 Master Job UID 与冻结 handoff 一致，仍为 active。该异常丢失底层 stderr，
不能事后断言一定是网络故障，也不能用错误摘要里的 current rule 推断 rule 失败。

基线源码存在以下差异：

- 两套 DAG 的只读 stage sensor 已有有限网络重试。
- GATK gate 的 Step3 子进程非零退出会直接落成 failed，先于 sensor 容错。
- WGS Step3 对 `kubectl query failed` 有按文本等待的兼容，但不足以区分
  认证/身份问题与连接故障，也不等于全链路恢复已实现。
- WGS 已有 resume_stage；后端当前明确限制 WGS CCE，GATK 不能直接调用。
- GATK SSH 派发失败、DagRun 失败投影也须与 runtime 的错误语义对齐。

选用“共用错误规则 + adapter 按原执行记录恢复”。只增加 Airflow 重试次数
不能修复底层已写入的错误终态；整步自动重跑则会重复创建/发布。
不合并两套 DAG，不建立新的连接恢复守护服务。

## 3. 错误分类与重试责任

| 类别 | 决策 |
| --- | --- |
| 明确连接超时、重置、临时不可达，HTTP 408/429/5xx | 对只读查询有限重试 |
| 认证、权限、参数错误 | 不自动重试；记录控制/监控错误，不据此判定远端分析失败 |
| 身份、request hash、generation、Master UID 不匹配 | 阻止恢复；不切换对象 |
| 权威执行记录确认业务失败或执行进程异常退出 | 真实步骤失败；不降级成成功 |
| 查询失败、对象消失但无可靠终态、模糊的通用报错 | 执行状态待确认；禁止推断成功/失败或重发有副作用的操作 |

共用规则：首次查询后最多重试六次，30 秒起指数退避，单次等待上限300秒。
每次请求须有明确超时；同时受原步骤总超时约束，不无限延长执行期限。
一次成功的权威查询结束本轮连接故障，后续正常轮询不消耗该轮重试预算。

职责边界：

- Airflow 到后端：复用已有 sensor 重试。
- runtime 到 Kubernetes/远端服务：由只读查询的直接调用层负责。
- 传输工具：保留原有内部重试，不套整步重跑。
- 证据桥只采集日志/事件；其异常不覆盖权威分析状态。

同一故障不能逐层获得新预算。runtime 报告重试耗尽后，sensor 不把它重新
当作一次尚未处理的临时 HTTP 错误。重连次数、首次错误时间、耗尽原因及
最后确认时间沿用已有步骤/操作 JSON 记录保存；进程重启或重复点击不能
静默重置同一恢复操作的预算。新的人工作业恢复操作可获得一轮新预算。

错误需包含脱敏类别、退出码/HTTP 状态及简短原因，不公开 token、配置正文、
带凭据 URL 或原始完整 stderr。如果 CCE runtime 已吞掉原因，应在其正式
源代码修复，再按原发布流程交付；不能靠上层字符串猜测，也不能改写已冻结
bundle。旧通用错误归为“未分类、待确认”，不无条件自动重试。

## 4. 各步骤恢复规则

| runtime 步骤 | 接回及续跑行为 |
| --- | --- |
| Step1 上传 | 原执行活跃则接回监控；确认进程退出后，用户续跑才复用 checkpoint 和成功对象补传 |
| Step2 创建 Master | 丢失响应先按原请求查询；已有 Master 则接回。只有明确原提交未发生且不存在在途创建，才允许同一请求重发 |
| Step3 分析监控 | 绑定原 Master UID 只读重连；真实成功继续下游，真实失败保留失败，不自动替换 Master |
| Step4 发布 | 查询原发布操作及记录；仍进行则等待，已完成则确认成功；无法确认时不再次发布 |
| Step5 下载 | 原下载仍活跃则接回；确认退出后，用户续跑复用 checkpoint 和已验证文件 |
| Step6 整理交付 | 接回原进程，或依据已有 journal/交付记录续做未完成部分；不重新下载，不覆盖已交付结果 |

Step2 的一次空查询不充分证明创建请求未到达；必须与已有派发/执行记录
一起确认，依靠原任务确定性身份与服务端防重复创建能力，不新增随机 Master。
Step4 同样不能将“未拿到响应”等价为“发布未发生”。

只做必要身份、活跃执行和恢复记录检查；不全量扫描输出、计算历史文件哈希
或重新验证整个 release。现有结果允许存在。同任务旧锁按现有归属和活跃性
处理；其他任务持锁或无法确认活跃性则停止，不强行解锁。

传输 lease 不因查询失败、Airflow task 失败或超时直接释放。只有现有权威
终态/归属条件满足才能释放，避免原上传/下载仍运行时引入第二份执行。
本方案不改变 lease 数量、池配置或并发限额。

## 5. Airflow、后端和页面状态契约

区分执行结果与监控健康度，复用 `monitoring_health`、`message` 和原步骤
JSON/执行记录，不新增整套业务状态。通用失败不能直接冒充执行终态 receipt。

| 场景 | 调度与展示 |
| --- | --- |
| 有限重连中 | 保留最后确认的执行状态/进度；显示“连接中断，正在重连”及最后确认时间 |
| 重试耗尽或控制错误 | 停止自动查询；显示“监控中断，执行状态待确认”和原因，提供人工恢复入口 |
| 重连查到原执行仍活跃 | 接回正常监控，不重新派发，不增加业务 attempt |
| 重连取得权威成功 | 同步原步骤成功，放行必要下游 |
| 取得权威失败 | 明确步骤失败，保留原失败原因与断点 |
| 权威分析成功但日志采集异常 | 分析成功，监控 degraded，提示“分析完成，日志采集异常” |

Airflow task/DagRun 可因监控耗尽或控制错误结束为 failed，但后端不得仅据此
将远端分析投影为失败。失败回调、周期状态同步、runtime receipt 导入必须
遵守同一规则；不能只改页面文案而保留后端错误终态。

耗尽后的最后 running 是“最后确认状态”，不能继续对外宣称实时正常运行。
Tracker 和详情使用同一监控健康度/时间字段，进度冻结并明确过期，不继续
凭时间推进预估进度。无权威成功不启动下游；不能将监控 task 标成 success
来绕过依赖。身份校验失败也不能伪装成成功。

## 6. 恢复入口与幂等

复用运行操作面板和认证，通过 adapter 补齐 GATK 的阶段恢复能力。共用动作
语义和操作记录，不将 WGS 的所有运行时逻辑直接套到 GATK，也不走会增加
业务 attempt 并重新 prepare 的旧 resume 路径。

人工点击后的先后顺序：

1. 验证当前任务/attempt/冻结目录与配置身份。
2. 查询原执行及已有恢复操作；重复点击返回同一操作。
3. 原执行活跃：仅恢复监控；原步骤成功：同步状态并继续必要下游。
4. 进程确认退出：当前人工操作授权在该步骤原有断点能力内续跑。
5. 无法确认活跃性：保持待确认，不启动第二份。

只读查询本身不增加 generation；确需新监控进程或步骤执行时，用现有
generation/retry 记录留痕，明确绑定原远端执行。原执行的可信终态只能经
当前恢复操作验证后归入当前状态，旧失败事件不能直接覆盖新执行。
清除的是新执行的旧终止时间，历史记录不删除。

重开范围限当前步骤/监控和必要下游，已成功前置步骤不变。保留原生信
Master 失败后的明确授权续跑机制，但本次不新增自动 Master 替换能力。
界面复用现有控件，按情况显示“恢复监控”或“续跑”，不新增独立恢复页面。
