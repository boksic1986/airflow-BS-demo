## 1. 目标与已确认决策

将样本资料、批次等待和实际分析分开，支持本地、云上通过共享文件交接，不让未入选样本继承批次 running/success 状态。

| 数据对象 | 职责 | AnalysisRun 关联 |
| --- | --- | --- |
| 新增独立样本查阅表 | sampleinfo、pending、来源与同步情况 | 不要求关联 |
| Intake 批次表 | 待下机、待数据就绪、待分析及异常 | 提交前为空，提交后保留关联 |
| 现有 Sample | 实际入选样本及分析状态、QC | 保持必须关联 |

核心决定：

1. 共享 pending 文件负责交接，数据库查阅表是文件的查询投影，不反向参与样本选择。
2. 现有 Sample/AnalysisRun 关系保留；主要改变 Sample 写入时机和当前 attempt 查询范围。
3. 待下机、待分析只在 Intake 按批次展示，不创建逐样本等待状态或占位 AnalysisRun。
4. 本地允许在数据库暂不可用时继续运行，恢复后补同步；文件交接本身失败不能忽略。
5. 从正式启用点开始同步生产范围，不自动导入历史测试数据。历史测试清理另行授权。
6. 生信规则、MEI、CCE 镜像、Heavy I/O 和 Step1–Step7 执行行为不属于本设计。

## 2. 现状与变更边界

当前 `Sample.analysis_id` 必填，唯一约束为 analysis_id + sample_id。现有发布将 selection_decision、selection_attempt 和 pending_reason 保存在 Sample metadata 中；本设计将纯候选、pending、excluded 从未来分析样本写入路径分离。

当前 Intake 的 chip_id/source_path 必填且唯一，analysis_id 可为空。因此“现有数据库不变”只指不推翻分析模型：新增查阅表和预下机 Intake 的最小迁移仍然必要。

当前 runtime gate 初代 pending 输入为完整表头的空表；后续 generation 可复用已验证的私有 pending 材料。WGS prepare 还会合并共享 pending 文件。不能把当前实现描述为“云上只以数据库 pending 为唯一来源”。

## 3. 分析样本与独立查阅表

### 3.1 Sample 只接收实际分析样本

- prepare 完成，验证 receipt schema、analysis_id、attempt、来源和完整样本集合后，按 selected 写入 Sample。
- candidate、pending、excluded 不再新建为分析样本；审核阶段读取现有准备快照，而不是先建立候选 Sample。
- Run Detail、Run Tracker、Batch Runs、Dashboard 和批次 QC 使用同一个当前 attempt selected 范围。
- 准备完成前显示“待确定分析范围”，不以候选数量代替分析数量。
- 审核取消只处理草稿/快照和现有取消记录，不消耗共享 pending，不产生分析样本。
- 历史真正参与过分析的 Sample、QC、rule 和 attempt 证据保留。本次未入选不能删除上次分析历史。
- 不只覆盖一个 latest selection 标记：当前范围读取当前 attempt receipt/范围快照；历史查询读取对应历史 attempt，缺少证据不能猜测。
- 旧批次没有完整范围材料时保留兼容逻辑，不据此推断删除。
- `QC Pending` 继续表示已入选样本尚无 QC；它不等于未入选的 pending 样本。

### 3.2 独立查阅模型

新增 `sample_reference`，不设必填 AnalysisRun 外键。它是来源记录的查阅模型，不是新的分析状态机，也不是可以回写 pending 的编辑器。

最低记录内容：样本/家系标识、允许展示的订单与批次信息、来源类型、受控来源 ID、源记录身份、内容版本、最后成功同步时间、pending 原因、同步异常/资料冲突，以及是否存在于该来源的最新完整快照。

身份与合并：

- pending 沿用现有身份规则，不只用 sample_id。订单组、样本编号、上机批次、数据编号共同区分重复上机和补测。
- 完整身份在受控文件边界内计算；数据库使用稳定的不透明身份键，订单展示沿用脱敏策略，不借新增表扩大临床字段入库范围。
- sampleinfo 以来源与源记录身份保存；无法可靠对应的记录分别保留，不能通过姓名、mtime 或家系相同强行合并。
- 无批次、无订单保持空值，不虚构 AnalysisRun 或上机批次。
- 不同来源不互相整行覆盖。pending 清单成员关系与 sampleinfo 资料分别保留；冲突显示来源和原因。
- 查阅表不参与运行/完成/失败样本统计，也不参与批次 QC 分母。

### 3.3 文件交接与投影同步

正式生产根目录为 `/sg2/50.ctapa/project/HWcloud/WGS_Clinical`，共享 pending 为该根目录下的 `prepare/pending_samples.tsv`。

- 本地、云上和未来 SGE 共用现有“独占锁 → 读最新 → 按身份合并 → 原子替换”入口。
- 仅移除本次明确 selected 的匹配 pending 身份，不能按整个家系删除，不能用旧 sampleinfo 覆盖 pending 结论。
- prepare 成功后尝试同步一次；后台独立同步周期默认 60 秒，检查已登记来源变化并补偿失败，不随 Intake 自动分析开关启停。
- 新来源仅来自批准的准备产物登记和正式启用后的 Samplelist 发现；不每分钟递归枚举历史项目或大型分析结果。
- 用完整来源快照和内容版本幂等导入。完整解析和校验成功后再事务更新，不发布半批记录。
- 数据库不可用时，只要文件交接已可靠完成，本地分析可以继续；后续从受控来源重试，页面展示最后成功同步时间和延迟。
- 源文件写入失败必须使准备失败，不能因为数据库同步是非阻断操作而吞掉错误。
- 来源文件缺失、不可读、解析失败时保留最后可靠投影，不将全部记录标为删除/解除 pending。
- 只有成功读取的完整新快照才能判断记录已退出该来源；退出 pending 不自动表示分析成功。
- 数据库投影不向文件回写；无网络时没有双向冲突合并或 DB 覆盖共享文件的动作。

## 4. 批次预登记与下机检测

### 4.1 Samplelist 发现和资料预抓取

复用 WGS 已配置的 Samplelist 来源目录，避免平台再维护一份相互漂移的硬编码路径。

- 识别类似 `Samplelist_20260911-152103_20260911A.txt` 的文件，提取批次 `20260911A`。
- 首次正式启用记录现有文件基线；之后新文件预登记，已登记文件内容修改按版本更新。基线文件后续修改不自动当作新批次，补录需显式操作。
- 文件连续两次扫描大小/修改信息稳定且完整解析成功后处理；读取前后再次核对，变化中的文件推迟处理。
- 同项目、平台、批次只有一个 Intake；重复导出更新来源，不重复创建批次或自动提交。
- 预抓取样本资料仅写查阅区域，禁止调用分析样本选择、消费 pending、创建分析项目目录或冻结分析配置。
- 预抓取失败是资料异常，不是 workflow failed；正式提交时仍执行原有准备和样本校验。

### 4.2 按批次绑定未知目录

状态：`待下机 → 待数据就绪 → 待分析 → 已提交`。有歧义时显示 `needs_review` 和具体原因。

- 未绑定批次轻量枚举 `/bi/fastq/T7_Fastq/` 一级目录名，按完整 `_批次_` 字段匹配。
- 不预测前后编号，不要求下机顺序，不按最新 mtime 选择，不对全部历史 BarcodeStat 做内容检查。
- 没有匹配则等待；唯一有效目录绑定实际路径；多个匹配进入 needs_review，不自动选一个或合并。
- 拒绝越过批准根目录的路径和不受支持的符号链接。绑定后固定该路径；失效时提示，不静默切到另一目录。
- 绑定后只检查该目录的 BarcodeStat 及现有数据就绪条件。
- BarcodeStat 出现仍需 FASTQ 配对、排除和完整性校验，不直接等同于可提交。
- 不再以 BarcodeStat mtime 晚于 scanner 启动时间作为唯一发现条件。
- 扫描周期沿用现有配置；不因新设计擅自加快生产轮询。

### 4.3 Intake 最小迁移与提交

- chip_id/source_path 在待下机阶段允许为空，解析并绑定目录后填入真实值，保留非空值的唯一性保护。
- 增加项目、平台、批次唯一身份，以及 Samplelist 来源版本和等待状态。历史行迁移时检查身份冲突，不猜测合并。
- AnalysisRun 在提交前为空，提交后保留关联，继续使用现有锁、提交防重与恢复逻辑。
- 自动提交仍受 scanner、auto-dispatch、正式启用时间门禁控制；查阅同步不绕过这些门禁。
- 手动/自动同时提交、扫描重试和已关联运行，不得产生第二个相同批次的初始分析；重分析走现有明确的 rerun 流程。
- Intake 页面以批次、状态、目录等待/数据异常和检查时间为主。样本资料链接只用于查阅，不作为调度依赖。

## 5. API、界面和存量兼容

- 保留现有分析样本接口；新记录只包含实际分析样本，明确当前 attempt 范围是否已确定。
- 新增分页只读样本资料接口，支持样本、家系、脱敏订单、批次、pending、同步异常筛选；不提供反向修改交接文件的接口。
- Intake API 支持尚未知晓的芯片、路径和 AnalysisRun 为空，返回等待状态及原因。
- Samples 页面区分“样本资料”和“分析记录”；交接状态不与 running/success 共用同一语义。
- 保持现有静默刷新规则、筛选和分页；不因后台同步清空列表。
- 普通接口不泄露不必要的真实文件路径、患者字段或配置。

存量处理不是自动删除迁移：

1. 先以现有 selected 过滤保持正确显示，保留历史分析记录。
2. 对误写入 Sample 的 pending 输出范围和数量差异，验证完整 receipt、历史实际参与情况和外键关联。
3. 用完整受控原始材料迁移资料和原因，不用隐私裁剪 receipt 拼造完整样本表。
4. 只有已确认从未参与分析、资料已安全迁移且关联核对完成的记录，才可进入单独批准的清理操作。
5. 来源不足、已参与历史分析或有歧义的记录保留并报告。

实施时同步更新数据库/API/前端/runtime/scanner 契约。当前文档任务不把拟议模型写成已经生效的接口或数据库结构。

## 6. 实施分期与验收

| 阶段 | 主要责任 | 独立交付 |
| --- | --- | --- |
| A：分析样本边界 | Backend / Workflow | selected-only 写入、attempt 查询和审核快照兼容 |
| B：资料查阅与同步 | Backend / Workflow / Frontend | 新表、只读接口、文件投影、离线补同步和资料页面 |
| C：预下机 Intake | Backend / Frontend | 最小迁移、Samplelist 发现、目录绑定、批次展示与提交防重 |

每阶段先添加 synthetic 回归，再实现最小改动。实施责任不表示本轮启动多个 agent 或已授权生产动作。

必须通过的场景：

- 12 候选、6 selected、6 pending：分析 Sample 新增 6 条，资料可查 pending 原因，所有当前分析计数和 QC 分母一致。
- rerun selected 范围变化不删除历史分析、不把旧 attempt 样本算进当前范围。
- 审核取消不消费 pending，不产生分析 Sample；QC Pending 不被误过滤。
- 并发 pending 写入、重复同步和离线恢复不丢其他批次、不重复资料记录。
- 数据库失败不破坏文件交接；文件写失败不发布成功准备；半写/读失败不批量解除 pending。
- 同 sample_id 不同身份、缺批次、跨源冲突不会强行合并或虚构 run。
- Samplelist 重复导出、批次下机乱序、未知前后编号、多个匹配目录和不安全路径。
- BarcodeStat 已有但 FASTQ 未就绪不提交；scanner/dispatch 关闭不提交；并发手动/自动只创建一次初始分析。
- 查阅表记录不进入分析统计；API 空值与前端等待状态正确，刷新保留筛选和分页。

运行时测试只在 BS10610 批准的缓存环境执行；不从 Docker Hub 拉取，不做整套 WGS 重验证或真实分析。文档验收仅检查链接、范围、状态措辞和差异，不替代后续远端验收。
